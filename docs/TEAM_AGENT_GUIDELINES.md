# 團隊 Agent 開發規範

| 項目 | 內容 |
| --- | --- |
| 文件版本 | V1.1 |
| 更新日期 | 2026-09-18 |
| 適用對象 | 全組組員，以及 Cursor、ChatGPT 等 Agent |
| 本文件用途 | 讓 Agent 在開發前先知道「誰負責什麼、什麼能改、什麼不能改」 |

> 這份文件是給 Agent 與組員共用的開發注意事項。  
> 目的不是加速一次寫完所有功能，而是避免 Agent 改到其他組員的程式、共用設定或尚未輪到的範圍。

---

## 1. 使用方式

開始請 Agent 幫忙寫程式前，請先讓它閱讀：

1. `docs/TEAM_AGENT_GUIDELINES.md`（本文件）
2. `docs/CURSOR_PROJECT_CONTEXT.md`
3. `docs/GitHub_團隊協作說明.md`
4. 與自己功能直接相關的文件

可直接複製下面這段給 Agent，並把名字改成自己的：

```text
請先閱讀 docs/TEAM_AGENT_GUIDELINES.md、docs/CURSOR_PROJECT_CONTEXT.md、docs/GitHub_團隊協作說明.md。

我是：<請填自己的名字>

先不要修改任何檔案。請先對照 TEAM_AGENT_GUIDELINES.md 第 3 節表格確認：
1. 我適用哪個 Git 分支。
2. 這個分支對應的負責範圍，以及可以改／不可以改什麼。
3. 我目前實際所在的分支是否與上表一致。
4. 本次任務會動到哪些檔案。
5. 有沒有需要改到共用檔案或其他組員負責的檔案。

規則：
- 只能在我適用的分支、負責範圍內修改。
- 不可以修改其他組員的程式。
- 不可以重構整個專案。
- 不可以實作完整 MVP。
- 未經我確認，不要 commit、push、merge。
```

---

## 2. 最高原則

1. **不要修改其他組員的程式碼。**
2. **只在自己的功能分支開發，不要直接改 `main`。**
3. **先確認目前分支，再開始修改。**
4. **一次只做目前任務需要的最小修改。**
5. **不確定能不能改時，先停下詢問，不要自行決定。**

Agent 不是專案負責人。它只能協助目前這位組員完成自己負責的小範圍任務。

### 3.1 如何確認自己適用哪個分支

每位組員開始開發前，用自己的名字對照上表，不要憑感覺選分支。

1. 在上表「負責人」欄找到自己的名字。
2. 同一列的「分支」就是自己應該使用的分支。
3. 執行 `git branch --show-current`，確認目前分支與上表一致。
4. 如果目前在 `main`，或其他人的 `feature/...` 分支，先停止修改，再切回自己的分支。
5. Agent 必須以上表為準；不可因為功能看起來有關，就改到其他組員的分支或檔案。

快速對照：

| 如果你是 | 你應該使用的分支 | 這次只處理 |
| --- | --- | --- |
| 永富 | `feature/login` | 登入／註冊 |
| 姿彣 | `feature/course-management` | 課程管理 |
| Ken | `feature/student-management` | 學生管理 |
| Ollie | `feature/messaging` | 訊息接收與處理 |
| 宇鈞 | `feature/admin` | 平台使用者管理 |
| 雄哥 | `feature/database` | 資料庫 Schema 與 Migration |
| 禹銨 | 看本次任務：資料庫用 `feature/database`；後端骨架／整合用 `feature/backend` | 一次只進一個分支 |

如果同一個人在上表出現超過一次：

- 先看這次任務屬於哪一個「主要負責範圍」
- 再進入對應的那一個分支
- 一次只在一個分支工作，不要同時改兩個分支的內容

## 4. 預計模組對照

資料夾尚未全部建立前，仍先用「模組名稱」判斷責任，不要因為檔案還沒分開就改別人的功能。

| 模組 | 預計位置 | 負責人 |
| --- | --- | --- |
| 登入／註冊 | `backend/api/auth.py`、對應 `services`、`schemas` | 永富 |
| 課程管理 | `backend/api/courses.py`、對應 `services`、`schemas` | 姿彣 |
| 學生管理 | `backend/api/students.py`、對應 `services`、`schemas` | Ken |
| 訊息 | `backend/api/messages.py`、對應 `services`、`schemas` | Ollie |
| 平台管理 | `backend/api/admin.py`、對應 `services`、`schemas` | 宇鈞 |
| 資料表與 Migration | `backend/models/`、`alembic/`、`docs/data_schema_v0.1.md` | 禹銨、雄哥 |
| 後端入口與共用設定 | `backend/main.py`、`backend/core/`、`app.py` | 禹銨 |

如果實際檔名與上表不同，以 Git 分支負責人為準，不要只看檔名猜測。

## 5. 共用檔案：改之前必須先問

以下檔案影響全組，Agent 不得自行大幅修改：

| 檔案 | 原因 |
| --- | --- |
| `app.py` | 目前全組共用的 FastAPI 入口 |
| `requirements.txt` | 套件變更會影響所有人的環境 |
| `Dockerfile` | 影響 Docker 建置 |
| `docker-compose.yml` | 影響全組開發環境 |
| `.gitignore` | 影響哪些檔案會被提交 |
| `.env` / Secret 相關檔案 | 不可提交，也不可寫入真實金鑰 |
| `docs/data_schema_v0.1.md` | 資料表由資料庫負責人維護 |
| `docs/CURSOR_PROJECT_CONTEXT.md` | 專案上下文，需全組對齊後再改 |
| `docs/GitHub_團隊協作說明.md` | 協作流程文件 |

如果任務「看起來一定要改共用檔案」，Agent 應該：

1. 先說明為什麼需要改。
2. 列出預計修改內容。
3. 等待使用者確認。
4. 只做最小修改。
5. 修改後提醒使用者告知組長或相關組員。

## 6. Agent 開始前必須先做

每次任務開始時，Agent 必須先檢查：

```bash
git branch --show-current
git status
```

確認結果必須符合：

1. 已用使用者的名字對照第 3 節表格，確認適用哪個分支。
2. 目前分支就是該組員應該使用的功能分支。
3. 不是 `main`，也不是其他組員的分支。
4. 沒有誤改到其他組員的檔案。
5. 本次任務範圍清楚，且屬於第一階段。

若目前分支與第 3 節表格不符，Agent 必須先停止，不要開始改檔。

## 7. Agent 禁止事項

### 7.1 程式與檔案

- 禁止修改其他組員負責的檔案。
- 禁止為了「程式比較漂亮」而重構無關程式。
- 禁止一次實作完整 MVP。
- 禁止把登入、課程、學生、訊息、管理員功能寫在同一個檔案裡硬塞完成。
- 禁止刪除、覆蓋、重新整理其他組員正在使用的資料夾。
- 禁止移動其他組員已經開始開發的檔案，除非使用者明確要求。

### 7.2 Git

- 禁止直接在 `main` 開發。
- 禁止 `git reset --hard`。
- 禁止 force push。
- 禁止修改 Git config。
- 禁止未經使用者要求就 commit、push、建立 PR、merge。
- 禁止覆蓋或丟棄其他組員尚未提交的修改。

### 7.3 資料庫與規格

- 禁止自行決定尚未定案的商業規則。
- 禁止一次建立全部資料表。
- 禁止手動改正式資料庫結構，Schema 變更必須走 Alembic。
- 禁止把 PRD／SRS 裡的完整 MVP 功能當成現在就要做。
- 禁止把「規劃中的功能」寫成「已經完成」。

### 7.4 資安

- 禁止把密碼、API Key、Token、Database URL 寫進程式或提交到 Git。
- 禁止提交 `.env`。
- 禁止在 Log 或文件中寫出真實 Secret。
- 禁止把密碼存成明碼。

## 8. Agent 允許事項

在「自己的分支」與「自己的模組」內，Agent 可以：

- 新增或修改自己負責的 API、Service、Schema、測試。
- 補上與自己功能直接相關的說明。
- 提出最小修改計畫，等使用者確認後再改。
- 發現其他模組有問題時，用文字回報，不要直接去改。
- 若現有結構還不完整，先延續現有寫法，不要大搬家。

---

## 9. 跨模組需求怎麼處理

如果 A 組員的功能需要 B 組員的 API、資料表或檔案：

1. Agent 不可直接修改 B 的程式。
2. 先寫出需要對方提供什麼。
3. 由使用者去找對方或組長協調。
4. 在自己的模組先用最小方式接上，例如先假設對方 API 之後會提供。
5. 不要為了自己方便，把對方功能重寫一份。

範例：

```text
正確：
「學生管理需要課程列表 API。目前不修改課程模組，先請課程負責人提供 endpoint。」

錯誤：
直接打開 courses.py，幫對方把課程 API 寫完。
```

## 10. 第一階段範圍

現在只做第一階段，不要自動擴充。

第一階段包含：

- 登入／註冊
- 課程管理
- 學生管理
- 訊息接收與處理介面
- 平台使用者管理
- 基礎資料庫 Schema
- 後端框架與模組整合

第一階段不要做：

- 公開課程首頁
- AI 課程推薦
- 完整 LINE AI 客服
- 完整堂數、收款、推廣、媒合流程

## 11. 建議的 Agent 工作流程

Agent 每次收到任務時，先用這個格式回答：

```text
Context Review
- 組員：...
- 適用分支（依第 3 節表格）：...
- 目前實際分支：...
- 目前負責範圍：...
- 本次可修改檔案：...
- 不可修改檔案：...
- 是否會碰到共用檔案：是／否

Plan
- 最小修改內容：...
- 影響檔案：...
- 是否需要其他人配合：是／否
```

使用者確認後才可以開始改檔。

完成後再用這個格式回答：

```text
Completed
- 做了什麼。

Changed
- 改了哪些屬於自己範圍的檔案。

Verification
- 如何測試。

Notes
- 有沒有碰到共用檔案、資料庫、或其他組員需要知道的事。
```

---

## 12. 組員自己也要遵守

Agent 會跟著使用者的指示走。組員請避免這樣下指令：

```text
請幫我把整個後端寫完。
請順便把登入、課程、學生、訊息都做掉。
請直接改 main。
請重構全部資料夾。
請把其他人的程式整理成更好的寫法。
```

請改成這樣：

```text
我在 feature/student-management 分支。
請只處理學生管理範圍。
先不要改其他模組。
先給最小修改計畫，等我確認再改。
```

## 13. 完成前檢查清單

送出給 Agent 的任務，或準備 commit 前，請確認：

- [ ] 已用自己的名字對照第 3 節表格，確認適用分支
- [ ] 目前實際分支與適用分支一致
- [ ] 沒有改到其他組員的程式
- [ ] 沒有未經確認改到共用檔案
- [ ] 沒有提交 `.env`、密碼、API Key
- [ ] 沒有一次做完不屬於自己的功能
- [ ] 修改範圍可以用一句話說明
- [ ] 需要其他人配合的地方已經寫出來
