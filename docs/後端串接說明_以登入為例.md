# 後端怎麼串起來：用登入當例子

這份給還不熟 FastAPI 的組員。以前學的是 Flask、PyMySQL、MySQL；現在專案用 FastAPI、SQLAlchemy、PostgreSQL。做事的順序其實一樣，只是檔案拆開、套件名字不同。

登入規則的細節看 `docs/登入註冊邏輯說明文件.md`。這份只說明「一個請求怎麼從網址走到資料庫，再走回來」。

---

## 1. 先用一句話看懂

使用者在瀏覽器按登入，FastAPI 接到 `/login`，檢查 Email 和密碼，到 PostgreSQL 的 `users` 表找出這個人。密碼對了，就把這個人的 `user_id` 放進 Cookie。下一次開頁面，後端看 Cookie 就知道是誰。

可以想成餐廳：

1. 客人把點餐單交給櫃檯。櫃檯是**路由**。
2. 櫃檯不自己進廚房翻帳本，交給負責規則的人。這是 **Service**。
3. 負責規則的人請資料員去查「這個 Email 有沒有帳號」。資料員是 **Repository**。
4. 帳本的每一列長什麼樣子，寫在 **Model**。真正的帳本是 **PostgreSQL**。

---

## 2. 以前的寫法，對到現在的檔案

| 以前 Flask + PyMySQL | 現在這個專案 | 在哪裡 |
| --- | --- | --- |
| `app = Flask(__name__)` | `app = FastAPI()` | `app.py` |
| `@app.route("/login", methods=["POST"])` | `@router.post("/login")`，再 `include_router` | `backend/routers/auth.py`、`app.py` |
| `request.form["email"]` | 函式參數 `email: str = Form(...)` | `backend/routers/auth.py` |
| `session["user_id"] = ...` | `request.session["user_id"] = ...` | 同一支登入函式 |
| `pymysql.connect(host, user, password, database)` | `.env` 的 `DATABASE_URL`，交給 SQLAlchemy | `backend/core/config.py`、`backend/core/database.py` |
| `cursor.execute("SELECT * FROM users WHERE email=%s", ...)` | `select(User).where(User.email == email)` | `backend/repositories/user.py` |
| `conn.commit()` / `conn.close()` | `db.commit()`；請求結束時 `db.close()` | Service 與 `get_db()` |
| MySQL 的一張表 | PostgreSQL 的 `users` 表 | `backend/models/user.py` |

PostgreSQL 就是另一種資料庫，角色和 MySQL 一樣：負責把資料存起來。SQLAlchemy 負責用 Python 物件去讀寫它，所以平常不用自己寫連線和大部分 SQL。

---

## 3. 程式啟動時先接上什麼

執行 `python3 app.py` 之後，發生這些事：

1. `app.py` 建立 FastAPI。
2. 加上 Session。登入成功後的 `user_id` 會放在瀏覽器 Cookie，後端用 `SESSION_SECRET_KEY` 保護它。
3. `app.include_router(...)` 把登入路由掛上來。沒有這一行，`/login` 不會通。
4. `backend/core/database.py` 用 `DATABASE_URL` 建立連線工具 `engine`，以及每次請求用的 `SessionLocal`。

`.env` 要有這兩行，否則程式啟動或連資料庫時會停住：

```text
DATABASE_URL=postgresql+psycopg://使用者:密碼@位址:5432/資料庫名稱
SESSION_SECRET_KEY=一串自己產生的隨機文字
```

`users` 這張表不是程式一啟動就自動長出來。表是用 Alembic 的 migration 建立的，檔案在 `alembic/versions/001_create_users_table.py`。Model 是 Python 裡的表格說明；migration 才是真正去資料庫建表的那一步。

## 4. 跟一次學生登入

學生在 `http://127.0.0.1:8000/login` 輸入 Email、密碼，按送出。瀏覽器對後端發：

```text
POST /login
```

### 第 1 站：路由

`backend/routers/auth.py` 的 `submit_login` 接到這個請求。

它做三件櫃檯的事：

- 拿出表單的 `email`、`password`
- 向 `get_db()` 要這一次請求專用的資料庫 Session
- 把這兩個東西交給 `authenticate_user`

Email 格式不對，就停在登入頁，顯示錯誤。這裡還沒查資料庫。

### 第 2 站：每次請求的資料庫 Session

`backend/core/database.py` 的 `get_db()`：

```text
打開一個 Session → 交給這次請求使用 → 請求結束就關掉
```

這和以前在 Flask 路由裡 `pymysql.connect()`，用完 `close()` 是同一件事。差別是 FastAPI 用 `Depends(get_db)` 自動幫每個請求做，路由不用自己寫開關。

### 第 3 站：規則

`backend/services/user.py` 的 `authenticate_user`：

1. Email 去掉空白並轉成小寫。
2. 請 Repository 用 Email 找人。
3. 找不到，回傳沒有這個人。
4. 找到了，用 Argon2 比對密碼。資料庫存的是 `password_hash`，不是明文密碼。
5. 密碼不對，一樣回傳沒有這個人。登入頁會顯示「Email 或密碼錯誤。」

### 第 4 站：查資料表

`backend/repositories/user.py` 的 `get_user_by_email` 相當於：

```sql
SELECT * FROM users WHERE email = '學生輸入的 email';
```

它查的是 `backend/models/user.py` 的 `User`。這個 class 的 `__tablename__ = "users"`，所以 SQLAlchemy 知道要去 PostgreSQL 的 `users` 表。

### 第 5 站：記住這個人

密碼正確後，路由做：

```text
清掉舊的 Session
request.session["user_id"] = 這個使用者的 id
```

Cookie 裡只放 id，不放密碼，也不放整包個人資料。

接著 `redirect_user_home` 依 `role` 帶去下一頁：

| role | 去哪 |
| --- | --- |
| student | `/student` |
| teacher | `/teacher` |
| admin | `/admin/teacher-applications` |

老師即使還在等審核，也可以登入，但頁面會停在等待審核。學生帳號若 `is_active` 是 false，登入會被拒絕。

### 下一次開頁面

例如打開 `/profile`。路由呼叫 `get_session_user`：

1. 從 Cookie 讀 `user_id`
2. 沒有 id，當成沒登入，導回 `/login`
3. 有 id，再用 Repository 的 `get_user_by_id` 到 `users` 表把這個人讀出來

所以「還在登入中」不是資料庫多記一筆登入狀態，而是瀏覽器帶著 Cookie，後端每次用 id 把人找出來。

登出是 `POST /logout`，把 Session 清掉，Cookie 裡的 `user_id` 就沒了。

## 5. 網頁和 JSON 走同一條路

現在測試頁用 HTML 表單打 `POST /login`。

以後前端改打 JSON，路徑是 `POST /api/auth/login`。它一樣呼叫 `authenticate_user`，一樣把 `user_id` 放進 Session，只是回傳 JSON，不回傳 HTML。

查「我是誰」是 `GET /api/auth/me`。這支路由寫了 `Depends(get_current_user)`，沒有 Cookie 就直接回 401。

## 6. 一張圖看完整條路

```text
瀏覽器 POST /login
        │
        ▼
app.py
  FastAPI 收到請求，Session 中介層先看 Cookie
        │
        ▼
backend/routers/auth.py
  submit_login：拿表單，跟 get_db() 要 Session
        │
        ▼
backend/services/user.py
  authenticate_user：檢查帳號與密碼規則
        │
        ▼
backend/repositories/user.py
  get_user_by_email：查這一列
        │
        ▼
backend/models/user.py
  User 對應 users 表
        │
        ▼
PostgreSQL
  回傳這一列
        │
        ▼
路由把 user_id 放進 Session，依角色轉到 /student 或 /teacher
```

註冊多一步：Service 先確認 Email 沒人用過，把密碼做成 `password_hash`，`db.add()` 後 `db.commit()` 才真正寫進 PostgreSQL。中間失敗會 `db.rollback()`，這次新增就不會留下半筆。

## 7. 你要加一個新功能時，照這個順序

例如「學生送出調課申請」：

1. 在 `backend/models/` 說明新表有哪些欄位。
2. 用 Alembic 加一支 migration，讓 PostgreSQL 真的有這張表。
3. 在 `backend/repositories/` 寫查詢和新增。
4. 在 `backend/services/` 寫規則，例如「只有這個學生的課可以申請」。
5. 在 `backend/routers/` 加路徑，例如 `POST /api/...`。
6. 若這支路由檔是新的，回到 `app.py` 加 `include_router`。
7. 需要登入的路由加上 `Depends(get_current_user)`。

路由只負責接請求和回結果。判斷規則放 Service。SQL 放 Repository。不要在路由裡直接寫一段 SQL。
